Lens × Moyai / Regression lab

Three concrete improvements to Lens.

Build trustworthy pass/fail results, useful evals from a repository, and a clear way to compare model or SDK changes. Start with the first two.

What to build

Proposed Lens features
1 · First

A failed test makes the Lens case fail

Add a typed checks field to the SDK and result API. The trusted test runner sends unit-test or workspace-verification outcomes alongside output and trace. Lens makes required checks authoritative.

Developer experience: “Failed · 2 required checks failed.” Click the case to see the failed assertions and trace. A judge saying success cannot override failed required checks; missing checks cannot pass.

Today, our local fix makes pytest fail correctly. Lens server badges still need this change.

2 · Next

Create useful evals from the repository

After Connect GitHub, Lens proposes tasks from existing tests and accepted bug fixes. Each gets a starting code snapshot, a clear task, required tools, and an executable verifier. The developer reviews and saves them.

Developer experience: “We found 3 regression tasks. Here is what each protects.” Before saving a case, prove the known fix passes and the original defect fails. No production traces required.

Moyai example: the provider-to-SDK routing bug from PR #178. The original code fails four checks; the accepted fix passes all sixteen.

3 · Then

Compare a model or SDK change from the UI

Select current and proposed configurations, then click Run comparison. Lens triggers GitHub Actions; the runner executes the Python agent against the same cases in separate runtimes. Lens receives checks, outputs and traces.

Developer experience: “6 passed · 1 failed · 1 incomplete,” with the exact model, SDK and commit on each side. Click a case for its failed check and trace. Infrastructure failures get a separate status.

The merged Run again button reruns an existing workflow at its original commit. Choosing a new configuration and explicitly pairing runs is additional product work.

Why these priorities: both models passed the four existing function tasks. In one matched repository-task pilot, the baseline completed and passed 16/16 checks; the smaller model exhausted the call budget without making the fix. This is one task and one paired pilot, not a general model ranking.

Already implemented in Moyai: stronger verifiers, local CI failure when verification fails, and separate dependency environments. The Lens product features above remain proposed.

Start from the repository, not an empty dataset

Proposed experience

One setup flow. A developer connects Moyai, confirms what Lens will execute, and gets useful coverage before any production traces exist.

Every case needs a starting state

Repository commit or minimal fixture, dependency image, input and necessary history, tool state, and bounded credentials or local substitutes.

Every case needs an observable outcome

Trusted test identifier, expected files or state, and pass-to-pass checks. A successful trace root alone does not prove correctness.

Every case must earn its place

A reference solution passes. A no-op and relevant broken versions fail. Unstable candidates stay out of the regression lane.

What a replay recipe should contain

Proposed portable case contract. This is a design sketch, not a shipped Lens configuration format.

case: repository-bugfix-001
source:
  repository: BerriAI/moyai
  revision: <pinned starting commit>
runtime:
  manifest: <versioned production configuration>
  image: <digest built from that revision's lockfile>
input:
  request: <reviewed user-visible task>
  history_fixture: <only if the task needs prior context>
environment:
  tool_fixtures: <local substitutes for external side effects>
verification:
  required: [workspace_tests, unchanged_behavior]
  bundle: <trusted held-out verifier revision>
provenance:
  origin: accepted_bugfix | reviewed_requirement | production_trace
  reproduction: reference_passes_and_negative_controls_fail

Implementation and remaining work

Not deployed

Prioritize a trustworthy verdict and a faithful comparison. Then grow coverage and make the result easy to act on.

First fixes implemented

Implemented · not deployed
  • ✓Expanded the four coding verifiers. All four previously missed bad implementations now fail, and correct reference solutions still pass.
  • ✓Independent verification failures and incomplete executions fail pytest even if a remote judge returns success. Results and traces are saved first.
  • ✓Base and candidate use their own frozen dependency environments. Native SDK selection follows production settings, including explicit overrides.
  • ✓Added reproducible mutation probes, a historical repository task and isolated Lens publication with verified baseline pairing.

Still needed: server-side enforcement of required deterministic checks, a versioned production configuration comparison, production prompt/history coverage, exact baseline binding in the normal CI contract, and independently held-out sensitivity trials. The fixed CI model does not cover environment-only model changes. No required branch-protection gate was enabled.

P0

Make deterministic failures authoritative

Record trusted runner checks alongside outputs and traces. A failed required check must fail the case without asking a judge to interpret a JSON boolean. Preserve the trace for debugging.

Acceptance: a completed root trace plus a failed workspace check is red in Lens and in CI. A missing required check cannot pass.
P0

Compare the actual before and after runtime

Install each revision from its own frozen lockfile. Resolve model, harness and prompt from the production configuration. Bind the candidate to its exact before-run ID and source SHA.

Acceptance: all three configuration mutations change the runtime under test; a candidate SDK change never overwrites the baseline SDK.
P1

Turn historical defects into permanent protection

Import the verified yield, compaction, large-image and routing controls. Add repository-editing and follow-up tasks. Retain the four function tasks as an explicitly labeled smoke suite.

Acceptance: historical broken variants fail, current behavior passes, and every outcome links to its reproducible proof or trace.
P1

Calibrate sensitivity and false alarms

Freeze independently authored held-out faults, repeat unchanged controls, and run paired base/candidate trials in alternating order. Separate incorrect results, agent limits and infrastructure errors.

Acceptance: publish the missed faults, case-level variability and inconclusive runs. Keep checks advisory until the agreed sensitivity and false-alarm targets are met.
P2

Generate reviewed coverage from repos and traces

Draft replay recipes from tests, accepted bug fixes and tool contracts. Later, sample sanitized production failures, corrections and long sessions. Verify each recipe before adding it to the regression suite.

Acceptance: no-trace onboarding yields a runnable starter suite; adding a trace creates a reviewed case and verifier change, not just another dataset row.
What a developer should see on a PR: “This model change regressed 2 of 18 stable tasks. Here are the failed assertions and the exact traces.” If execution failed before grading, say that and show the cause. No invented confidence score.
